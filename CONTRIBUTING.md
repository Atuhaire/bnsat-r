# Contributing to BNSAT-R

Thank you for your interest in contributing to BNSAT-R.

BNSAT-R is an open-source research initiative investigating the security, operational resilience and recoverability of Bitcoin full-node deployments.

We welcome contributions from researchers, developers, security professionals, infrastructure engineers and other technically interested contributors.

---

## How You Can Contribute

Contributions may include:

* Research literature;
* Academic papers;
* Technical references;
* Existing open-source projects;
* Research methodologies;
* Experimental ideas;
* Data analysis;
* Documentation;
* Code;
* Testing;
* Technical review;
* Research critique.

---

## Research Contributions

If you identify relevant research, please open an issue or submit a pull request where appropriate.

Please include:

1. Title;
2. Author(s);
3. Publication date;
4. Source;
5. Summary;
6. Relevance to BNSAT-R;
7. Potential research gap or limitation.

---

## Technical Contributions

Before submitting code, please open an issue describing:

* The problem;
* The proposed solution;
* Why it is relevant;
* Whether existing tools already address the problem.

We strongly encourage discussion before significant implementation work begins.

---

## Avoiding Duplication

BNSAT-R follows the principle:

> **Collaborate Before Duplicating.**

Before proposing a new tool, contributors should investigate whether an existing open-source project already provides similar functionality.

Where appropriate, we may:

* Contribute upstream;
* Extend an existing project;
* Collaborate with maintainers;
* Build complementary tooling.

---

## Research Integrity

Contributors should:

* Clearly distinguish evidence from opinion;
* Cite sources;
* Avoid unsupported claims;
* Document assumptions;
* Report negative findings;
* Avoid manipulating results;
* Disclose conflicts of interest.

Research findings should not be altered simply because they contradict an initial hypothesis.

---

## Experimental Safety

All experiments must be conducted in:

* Controlled environments;
* Dedicated test systems;
* Virtual machines;
* Or systems for which explicit authorisation has been obtained.

Do not intentionally disrupt public infrastructure.

Do not conduct unauthorised security testing.

Do not scan or probe systems without permission.

---

## Pull Requests

Pull requests should:

* Clearly explain the purpose;
* Reference an issue where applicable;
* Include supporting evidence;
* Include documentation where necessary;
* Be technically reproducible.

---

## Code Review

Contributors should expect technical review.

A contribution may be:

* Accepted;
* Requested for modification;
* Deferred;
* Rejected.

Rejection does not necessarily mean that the contribution lacks value.

The project may reject contributions that are outside the current research scope or duplicate existing work.
